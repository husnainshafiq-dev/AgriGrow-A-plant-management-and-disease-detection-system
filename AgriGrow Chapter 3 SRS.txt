Requirement Analysis 


3.1 Introduction to Requirement Analysis 

This chapter presents a structured and formal specification of system requirements for AgriGrow. The purpose of this chapter is to clearly define what the system shall accomplish before proceeding to the system design phase. The requirements documented in this chapter serve as a contractual foundation for implementation, validation, and system testing. The requirement analysis includes requirement elicitation techniques, identification of stakeholders, use case modeling, functional requirements, non-functional requirements, and external interface requirements. All requirements are written in measurable and testable format using standard requirement engineering principles. AgriGrow is specifically tailored to address the needs of local farmers by providing offline-capable AI diagnostics for regional crops including wheat, rice, corn, pepper, potato, and tomato, ensuring robust accessibility in low-connectivity rural areas. 


3.2 Requirement Elicitation Techniques 

This section describes the techniques used to gather and refine system requirements. Requirement elicitation ensures alignment between stakeholder expectations and system capabilities. Requirements for AgriGrow were identified using the following techniques: 

Stakeholder interviews to capture user expectations regarding language barriers and offline operational constraints. 

Literature review of local agricultural challenges and crop disease patterns (e.g., wheat rust, rice blight). 

Analysis of existing solutions (like Plantix) to identify critical functional gaps, primarily the heavy reliance on continuous internet access. 

Dataset examination and feasibility study to ensure MobileNetV2 can accurately detect localized crop diseases on mobile devices.

3.4 System Overview 

The proposed AgriGrow system operates within a structured Progressive Web App (PWA) architectural environment designed to support modular interaction between user interfaces, local processing logic, and cloud data synchronization. The system supports role-based interactions, enabling farmers to access core diagnostic features both online (via a server-side Python/TensorFlow inference engine) and offline (via a TensorFlow.js fallback cached in the browser), while allowing administrators to manage system data online. The system boundary encompasses the React PWA client, the Node.js/Express API server, the Python ML microservice, and MongoDB cloud storage. It ensures secure communication between internal modules and external services, such as the OpenStreetMap/Leaflet mapping services, when network connectivity is restored, ultimately creating a seamless and resilient digital farming assistant.

3.7 Non-Functional Requirements 


3.7.1 Performance Requirements 

PER-1: The system shall load the main dashboard within 2 seconds under normal operating conditions. 

PER-2: The offline prediction response (Crop Doctor) shall be generated within 3 seconds of image capture. 


3.7.2 Security Requirements 

SEC-1: The system shall implement secure authentication mechanisms using JWT. 

SEC-2: Passwords shall be encrypted using secure hashing algorithms (
bcrypt
). 

SEC-3: Sensitive data synchronized to the cloud shall be transmitted using HTTPS protocol. 


3.7.3 Reliability Requirements 

REL-1: The system shall maintain 100% availability for its core AI diagnostic module via offline PWA service workers. 

REL-2: Network failures during community post uploads shall not result in data loss; data shall be queued for later sync. 


3.7.4 Usability Requirements 

USE-1: The interface shall be intuitive, featuring large touch targets for field environments. 

USE-2: The system shall be responsive with an English-language interface. Localization into regional languages (Urdu, Punjabi) is targeted for future phases. 


3.7.5 Scalability Requirements 

● SCA-1: The backend database design (MongoDB) shall support large datasets and horizontal scaling as user registrations increase. 


3.7.6 Maintainability Requirements 

● MAIN-1: The system shall follow a modular architecture to allow AI model weights to be updated without modifying the core application shell. 


3.8 External Interface Requirements 


3.8.1 User Interface Requirements 

UI-1: The system shall provide a graphical user interface optimized for mobile dimensions. 

UI-2: Navigation shall remain consistent across modules via header action buttons and in-page back navigation. 


3.8.2 Hardware Interface Requirements 

HI-1: The system shall require access to the device's camera module for image capture. 

HI-2: The system shall require a mobile device with a minimum of 2GB RAM to execute the TensorFlow.js models efficiently. 


3.8.3 Software Interface Requirements 

● SI-1: The system shall interact with a NoSQL database (MongoDB) for remote storage. ● SI-2: Third-party mapping services (OpenStreetMap via Leaflet.js, Esri satellite tiles) and Gemini AI API shall be securely integrated. 


3.8.4 Communication Interface Requirements 

CI-1: The system shall use HTTPS protocol for secure backend communication. 

CI-2: RESTful APIs shall be used for data synchronization between the PWA and the Node.js server. 


3.9 Assumptions and Dependencies 

The system assumes the user's mobile browser supports modern web standards (WebAssembly and Service Workers). 

The system depends on OpenStreetMap tile availability for map display and Leaflet.js for area calculations. 

The accuracy of the offline AI models is dependent on the conditions strictly present within the training datasets (wheat, rice, corn, pepper, potato, tomato).
