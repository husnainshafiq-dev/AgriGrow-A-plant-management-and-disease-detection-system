Software Design



4.1 Introduction to Software Design


This chapter presents the detailed software design of the AgriGrow system. It translates the requirements identified in Chapter 3 into structured architectural, behavioral, and data models. The purpose of this chapter is to provide a clear blueprint for system implementation, ensuring maintainability, scalability, and modular development. This chapter includes architectural design, UML models, data flow models, and database design specifically tailored for a machine learning-embedded Progressive Web Application (PWA).



4.2 Design Methodology and Software Process Model



4.2.1 Design Methodology


The AgriGrow project follows a Layered Architecture combined with the Model-View-Controller (MVC) design pattern for its backend, alongside a Data-Centric Edge AI approach for its frontend inference.


Justification: A layered MVC approach perfectly suits the MERN stack (MongoDB, Express.js, React.js, Node.js), cleanly separating the user interface (React PWA) from business logic and data routing (Node/Express). The Edge AI approach is crucial because running TensorFlow.js models directly within the React layer enables the strictly required offline functionality.


Design Principles: The design strictly adheres to the Separation of Concerns (SoC) and DRY (Don't Repeat Yourself) principles, ensuring that AI inference logic is decoupled from standard API communications.



4.2.2 Software Process Model


The project follows the Agile Scrum model.


Justification: Developing an AI-powered web application involves continuous refinement of machine learning models and user interfaces. Agile allows for high adaptability.


Iteration Cycles: Development is divided into 2-week sprints. Early sprints focus on PWA shell development and model training (using Python/TensorFlow-Keras), while later sprints focus on integrating TensorFlow.js for in-browser offline inference and Leaflet.js for geospatial mapping.


Testing Integration: Each sprint concludes with unit testing of the specific module (e.g., testing the AI confidence threshold or offline caching mechanisms) before integrating it into the master branch.



4.3 System Overview


The AgriGrow system serves as a bridge between local farmers and advanced agricultural data. The system boundary encapsulates the React-based PWA (running on the user's mobile device), the Node.js backend server, and the MongoDB cloud database. External actors include the Farmers (end-users), Administrators, and the Google Maps API (used for geospatial area calculations).






4.4 Architectural Design


AgriGrow employs a modern 3-tier architecture with an added Edge Computing layer.


Presentation Layer (Client): A React.js Progressive Web App utilizing Service Workers for offline caching of application shell and AI model weights. UI is currently English-only.


Edge Inference Layer (Client-Side AI): Primary inference runs server-side via a persistent Python/TensorFlow process. A TensorFlow.js fallback is configured for offline use in the browser. The MobileNetV2 model supports 28 disease classes covering wheat, rice, corn, pepper, potato, and tomato crops.


Business Logic Layer (Server): An Express.js/Node.js API that manages user authentication, synchronizes offline data, and proxies requests to the Agri-LLM.


Data Layer (Database): MongoDB for scalable NoSQL data storage.

4.7.2 Database Architecture


AgriGrow utilizes a Client-Server architecture with a Cloud NoSQL Database.


Local Storage: The PWA uses IndexedDB and Cache API to store TF.js model weights, offline diagnostic logs, and localization JSON files.


Cloud Storage: MongoDB Atlas is used as the primary cloud database, allowing flexible schema design which is ideal for storing unstructured agricultural queries and variable community post data.

4.9.3 Relationships Between Tables


One-to-Many (1:N): One User (Farmer) can generate multiple Diagnostic Logs and multiple Yield Estimates over time.


One-to-Many (1:N): One User can generate multiple Advisory records and Cost Estimations.



4.9.4 Security and Data Integrity


To ensure confidentiality and integrity, the following measures are implemented:


Password encryption using bcrypt before storing in MongoDB.


Role-Based Access Control (RBAC) enforced via JWT (JSON Web Tokens) to secure backend API routes.


Mongoose schema validations to prevent malformed data injection.


Offline data integrity is maintained using unique UUIDs generated on the client-side before cloud synchronization to prevent duplicate log entries.



4.9.5 Scalability Considerations


The database design incorporates NoSQL scalability mechanisms:


Horizontal Scaling: MongoDB supports replica sets and sharding to distribute database load.


Indexing: Indexes are applied to user_id and timestamp fields in the Diagnostic Logs and Community collections to accelerate read queries.


Edge Offloading: By performing the heavy image processing inference on the client's device via TensorFlow.js, backend server processing load is massively reduced, inherently scaling the system to thousands of concurrent users.



4.10 Chapter Summary


This chapter presented the comprehensive software design of the AgriGrow system. It translated the functional requirements into a structured Layered MVC architecture, uniquely integrating an Edge Computing layer to satisfy the offline AI processing mandate. The Agile design methodology was justified to accommodate iterative machine learning integration. Detailed UML models—including activity, class, sequence, and state diagrams—were documented to map out local inference, user management, and synchronization behaviors. Furthermore, data flow diagrams and the MongoDB NoSQL database design were detailed through ERDs and data dictionaries, establishing a secure, scalable, and highly available technical blueprint ready for the implementation phase. The primary ML inference is handled server-side via a persistent Python/TensorFlow process, with a TensorFlow.js browser-based fallback for offline scenarios. Geospatial features use Leaflet.js with OpenStreetMap rather than Google Maps API.
